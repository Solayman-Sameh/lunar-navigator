## Numerical acceptance and parity

These rules define the recommended N profile and implementation tests; no test listed here has been executed.

| Layer | Required check |
| --- | --- |
| Pre-export science | Independent analytic/hand-computed fixtures use binary64; integer visible/run counts agree exactly; fractions within 1e-12 and hours within 1e-9 h. Do not compare a rounded 0.333 value to 1/3 at 1e-6. |
| Independent Horizons comparison | Compare the same physical observer/settings/time/precision; allow half a unit in the last source-reported decimal place plus 1e-10 degrees for numeric conversion. Different source revisions must be identified rather than hidden inside tolerance. |
| Authoritative JSON recommendation | Preserve round-trip binary64 numeric values (shortest round-trip decimal or 17 significant digits); no NaN/Infinity; no decimal rounding of coordinates, heights, angles, thresholds, metrics, or scores. Reconstruct exported science and require exact integer masks/counts, fractions within 1e-12, hours within 1e-9 h. |
| Cross-engine angles and skyline | C# parity math uses binary64 and identical periodic formula; absolute computed-angle/interpolation tolerance 1e-10 degrees. This is an arithmetic budget, not a physical error bar. |
| Strict visibility and boundary handling | In Python science, compare clearance c=el-H-margin strictly to zero: equality hidden, no scientific epsilon shift. For cross-engine independent replay, require identical flags whenever abs(c)>1e-10 degrees. For abs(c)<=1e-10, count/report boundary samples separately; use authoritative stored flags for common metrics, never count a mismatch as an ordinary PASS or as missing-terrain UNKNOWN. Production publication requires every boundary sample's handling documented, not a blanket discarded mismatch. |
| Metrics/ranking parity | Common stored masks yield identical run lengths and integer sums; fractions within 1e-12, hours within 1e-9 h, score within 1e-12. Use the authoritative exported ordering for exact/near ties; independently verify hard requirements from unrounded metrics. |
| Rounded presentation | Three-decimal displays use nearest decimal with ties-to-even; negative zero displays as zero; azimuth rounded to 360 displays as 0. Value error <=0.0005 plus decimal conversion error. Validate presentation against its rounding rule, never against full-precision tolerances and never use it to recompute science. |
| If three-decimal scientific exchange is retained | N is NOT adopted. Need a separate approved canonical quantized-data policy, rederived flags/metrics, 0.0005-scale scalar tolerance, coordinate displacement accounting, and a decision audit that blocks opportunities when quantization changes qualification/ranking. Merely widening a tolerance while retaining inconsistent flags is unacceptable. |

Geometric fallback is an ideal reference sphere: if no verified ground elevation exists, explicitly choose z=0 on R=1,737,400 m and h=2 m for that model, query that model observer, and disclose that this is not verified actual site altitude. A terrain result uses the real validated observer. A fallback cannot claim their tracks represent precisely the same observer unless the positions agree.

Plan-preserving terrain geometry uses the plan's pixel bins and Cartesian points. For a pixel P and observer O in a common lunar frame, d=P-O, e=d dot east, n=d dot north, u=d dot up; az=atan2(e,n) modulo 360 and elevation=atan2(u,hypot(e,n)). Do not subtract d²/(2R) again. A reference spherical DEM must include its tangent neighborhood (roughly sqrt(2*R*h) range for small h) before applying the 0.02-degree raster tolerance. Finite range and missing near-field obstacles remain uncertainty limits.
