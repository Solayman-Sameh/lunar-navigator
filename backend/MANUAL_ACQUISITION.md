https://ssd-api.jpl.nasa.gov/doc/horizons_file.html .

## Run this once in a normal Windows PowerShell window outside ChatGPT/Codex

```powershell
Set-Location -LiteralPath 'C:\Users\user\Documents\Unity\LunarNavigator'; & '.\backend\.venv\Scripts\python.exe' '.\backend\acquire_horizons.py'
```

This uses the existing backend venv and tested client, performs one GET attempt
per target, retains complete original response bodies (including rejected bodies)
and errors, and never changes proxy/TLS settings. Each execution creates a new
`backend/data/runs/local-horizons-UTC-uniqueid/` directory and prints its exact path.
No old run or browser-saved original is overwritten. No package installation or
Unity/contract modification is performed. Keep any organization-required network
settings; if HTTP remains unavailable, use the browser import below.

Expected request: custom Moon site coord@301, latitude -89.5 degrees, longitude
0 east, nominal altitude 0.002 km above Horizons' reference sphere (2 m, not actual
DEM ground), Sun 10 and Earth 399, 2026-12-01T00:00:00Z through
2026-12-04T00:00:00Z, hourly, 73 endpoint-inclusive samples per body. All options
are generated by the existing HorizonsRequest.params() and URL-encoded. Output
is quantity 4, apparent AIRLESS azimuth/elevation, UTC/zero offset, CSV headings,
seconds precision and no daylight/elevation filtering. This is a diagnostic test
coordinate, not a verified landing-site recommendation.

Then run this import command from a normal PowerShell window:

```powershell
Set-Location -LiteralPath 'C:\Users\user\Documents\Unity\LunarNavigator'; & '.\backend\.venv\Scripts\python.exe' '.\backend\acquire_horizons.py' --import-dir '.\backend\data\horizons_inbox'
```

Import makes NO network call. It copies the exact saved bytes into a fresh run's
`raw/sun.json` and `raw/earth.json` BEFORE parsing, records original paths/hashes,
and uses the existing strict parser to verify source/target/observer/frame/radius,
UTC endpoints/count/cadence, finite angles/ranges and exact Sun/Earth pairing.
The existing client recognizes the observed API 1.2 profile. If another signature
version is returned, the original bytes are preserved and import fails pending
review; never change a source signature to make a test pass. HTML saves, API
errors, missing/partial tables and mismatched timestamps fail with saved evidence.
Imported data are explicitly labeled user-saved, not freshly fetched by Python.

## Files and success checks

Any received/imported raw response bytes are retained before validation.
After both actual responses pass validation, CSV/plot outputs are generated:

- `raw/sun.json`, `raw/earth.json`: unchanged original envelope bytes plus hashes.
- `raw/sun-result.txt`, `raw/earth-result.txt`: decoded source result text.
- `sun.csv`, `earth.csv`, `combined.csv`: full-precision parsed UTC/azimuth/elevation.
- `elevations.png`: both real elevation curves versus UTC.
- `validation.json`: actual counts, source headers, pairing/numeric/physical checks,
  output checksums, source/import provenance and final PASS/FAIL.

A missing plot, invalid source or failed check never earns PASS. Inspect the actual
PNG afterward; automatic output generation does not assert visual inspection or
mark T006 complete. Bring back the printed run path, validation.json and plot for
review. The script does not publish scientific JSON or change task checkboxes.
